## 🔴 Problem — 아쉬웠던 것 / 막혔던 것

- **Swagger 문서 페이지가 403으로 보였던 문제**: springdoc-openapi 2.6.0을 썼더니 `/v3/api-docs`에 접근할 때마다 403이 떴다. 서버 로그를 까보니 실제로는 403이 아니라 `NoSuchMethodError: ControllerAdviceBean.<init>` 예외가 나면서 Spring Security의 예외 처리 필터가 그걸 403으로 덮어버린 거였다. 원인은 springdoc 2.6.0이 Spring Boot 3.4.0(Spring Framework 6.2.0)과 버전이 안 맞았던 것 — springdoc을 2.8.5로 올리니 바로 해결됐다.
- **Docker 이미지 빌드가 마지막에 실패**: EC2에서 `docker compose up --build`를 돌렸더니 `compose build requires buildx 0.17.0 or later`라는 메시지와 함께 멈췄다. 로컬 Docker Desktop에는 buildx가 기본으로 들어있어서 몰랐는데, EC2에 `dnf install docker`로 설치한 패키지에는 buildx 플러그인이 같이 안 딸려왔다. GitHub에서 buildx 바이너리를 받아 `/usr/libexec/docker/cli-plugins/docker-buildx`에 직접 넣어주고 나서야 빌드가 됐다.
- **EC2 SSH 접속이 갑자기 안 됨**: 재부팅까지 해봤는데도 SSH(22번 포트)만 계속 타임아웃 났다. 다른 서비스(8080)는 멀쩡히 응답해서 서버 자체 문제가 아니란 건 알았는데 원인을 못 잡다가, 서버의 `journalctl -u sshd` 로그를 보고서야 원인을 찾았다 — 내가 `curl ipify.org`로 확인한 공인 IP(`211.235.67.5`)와 실제로 서버가 받아들인 접속 IP(`211.235.66.128`)가 서로 달랐다. 테더링 회선이라 트래픽 종류에 따라 나가는 경로(IP)가 다르게 잡힌 것 같다. 보안그룹을 서버 로그 기준 진짜 IP로 다시 맞추자 바로 풀렸다.
- Security를 붙이는 순서도 아쉬웠다. 2일차엔 인증이 없는 상태로 CRUD부터 만들고, 3일차에 JWT를 끼워 넣는 순서로 갔는데, 그러다 보니 컨트롤러의 `@RequestParam Long userId`를 나중에 전부 `@AuthenticationPrincipal User user`로 갈아엎어야 했다. 처음부터 인증 구조를 잡고 CRUD를 얹었으면 이 리팩터링이 없었을 것 같다.

## 🟡 Try — 다음엔 이렇게

- 의존성 버전(springdoc 등)은 Spring Boot 버전과 호환되는지 먼저 확인하고 넣기 — 안 맞으면 엉뚱한 에러 코드로 나타나서 원인 찾기가 더 오래 걸린다.
- Docker 관련 도구(buildx 등)는 EC2 세팅 스크립트에 처음부터 다 포함해두기.
- 배포 서버 접속이 안 될 땐 내 쪽 IP를 curl로 확인하지 말고 서버 로그(`journalctl` 등)부터 먼저 보기.
- 인증(Security) 구조를 먼저 잡고 그 위에 CRUD를 얹는 순서로 진행하기 — 나중에 갈아엎는 리팩터링을 줄일 수 있다.

## 📚 무엇을 배웠나 (Learned)

- JWT 인증은 로그인해서 토큰 발급하는 걸로 끝이 아니라, 매 요청마다 필터에서 토큰을 검증하고 SecurityContext에 넣어줘야 컨트롤러에서 "로그인한 사용자"를 알 수 있다는 걸 직접 구현하면서 이해했다.
- "본인 데이터만 접근"은 결국 모든 조회 쿼리에 예외 없이 `user_id` 조건을 거는 것뿐이다. Repository 메서드 이름에 `AndUserId`를 붙이는 습관을 들이니 실수가 줄었다.
- 로컬에서 되던 게 서버에서 그대로 되는 게 아니다(buildx 사건). 배포 환경은 따로 확인해야 한다.

## 🚧 가장 크게 막혔던 지점 (자세히)

4일차 EC2 배포 중 SSH 접속이 갑자기 안 됐다. 원래 쓰던 EC2가 재부팅해도 SSH만 막혀있고 다른 서비스(8080)는 멀쩡히 떠 있어서 처음엔 원인을 전혀 못 잡았다. 결국 서버를 하나 새로 만들어서 옮겼는데, 새 서버에서도 SSH가 똑같이 안 되는 걸 보고 나서야 "이거 서버 문제가 아니라 내 쪽 네트워크 문제구나"라는 걸 알아챘다. 서버의 sshd 로그(`journalctl -u sshd`)를 열어보니, 내가 curl로 확인했던 공인 IP와 실제로 서버에 접속을 시도한 IP가 서로 달랐다 — 테더링 회선이라 트래픽 종류에 따라 나가는 경로(그리고 IP)가 다르게 잡히는 것 같았다. 보안그룹을 실제 접속 IP 기준으로 다시 맞추고 나서야 풀렸다.
