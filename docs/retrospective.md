# 머니로그 회고

## 프로젝트 한 줄 요약

5일 동안 자바부터 배포까지 배운 걸 전부 써서 혼자 만들어 본 개인 가계부 서비스.

## Keep - 계속 하고 싶은 것

- 기능 하나 만들 때마다 서버를 띄워서 curl로 직접 호출해보고 넘어갔다. 덕분에 "다 짰는데 안 돌아가는" 상황이 없었다.
- 커밋을 일차별로 쪼개서 남겼더니 나중에 뭘 언제 했는지 찾기 편했다.
- 일차별로 할 일을 정해두고 그 순서대로 갔다. 4일차 배포에서 크게 막혔는데, 앞의 3일이 이미 끝나있어서 배포 문제에만 집중할 수 있었다.

## Problem - 막혔던 것

**1. Swagger 화면이 403으로 나옴**

`/v3/api-docs`에 들어가면 계속 403이 떴다. 처음엔 SecurityConfig에서 permitAll을 잘못 썼나 싶어서 경로를 이렇게 저렇게 바꿔봤는데 소용없었다. 서버 로그를 보니 진짜 원인은 권한 문제가 아니라 `NoSuchMethodError: ControllerAdviceBean.<init>` 이라는 에러였다. springdoc-openapi 2.6.0이 Spring Boot 3.4.0이랑 안 맞아서 나는 에러였고, 2.8.5로 올리니까 바로 됐다.

**2. 도커 빌드가 마지막에 멈춤**

EC2에서 `docker compose up --build`를 했더니 `compose build requires buildx 0.17.0 or later` 라고 뜨면서 멈췄다. 내 컴퓨터의 Docker Desktop에는 buildx가 처음부터 들어있어서 몰랐는데, EC2에 `dnf install docker`로 깐 도커에는 buildx가 없었다. 깃허브에서 buildx 파일을 받아서 `/usr/libexec/docker/cli-plugins/` 안에 넣어주니 빌드가 됐다.

**3. EC2에 SSH가 안 붙음**

가장 오래 걸린 문제라서 아래에 따로 적었다.

**4. 시큐리티를 나중에 붙인 것**

2일차에는 로그인 없이 CRUD부터 만들고, 3일차에 JWT를 끼워넣는 순서로 갔다. 그러다 보니 컨트롤러에 임시로 넣어뒀던 `@RequestParam Long userId`를 전부 `@AuthenticationPrincipal User user`로 다시 고쳐야 했다. 처음부터 로그인 구조를 잡고 시작했으면 이 작업은 안 해도 됐을 것 같다.

## Try - 다음엔 이렇게

- 라이브러리 넣기 전에 스프링 부트 버전이랑 맞는지 먼저 확인하기. 버전이 안 맞으면 엉뚱한 에러로 나와서 원인 찾기가 훨씬 오래 걸린다.
- 배포 서버에서 뭐가 안 되면 내 쪽에서 추측하지 말고 서버 로그부터 보기.
- 로그인/인증 구조를 먼저 잡고 그 위에 기능을 얹기.

## 무엇을 배웠나

- JWT는 로그인할 때 토큰 한 번 주고 끝나는 게 아니라, 요청이 올 때마다 필터에서 토큰을 확인하고 SecurityContext에 넣어줘야 컨트롤러에서 "지금 로그인한 사람"을 알 수 있다는 걸 직접 만들어보면서 알았다.
- "내 데이터만 보이게" 하는 건 결국 모든 조회 쿼리에 빠짐없이 `user_id` 조건을 거는 것이었다. Repository 메서드 이름에 `AndUserId`를 붙이는 습관을 들이니까 빼먹는 일이 줄었다.
- 내 컴퓨터에서 되는 게 서버에서도 되는 건 아니다. (buildx가 없어서 빌드 실패)
- 처리 안 한 예외가 나면 스프링이 `/error`로 다시 보내는데, `/error`가 시큐리티로 막혀 있으면 진짜 에러 내용은 안 보이고 전부 403으로만 보인다. 이것 때문에 원인을 두 번이나 헤맸다.

## 가장 크게 막혔던 지점

**증상**

4일차에 EC2로 배포하려는데 SSH 접속이 계속 타임아웃이 났다. 그런데 같은 서버의 8080 포트(전에 배포해둔 앱)는 브라우저에서 잘 열렸다. 포트 하나만 안 되는 게 이상했다.

**시도한 것들**

1. 보안그룹에서 SSH(22) 허용 IP를 지금 내 IP로 바꿔봤지만 그대로였다.
2. 네트워크 ACL이랑 인스턴스 상태 검사(3/3 통과)를 확인했는데 다 정상이었다.
3. AWS 콘솔에서 EC2 Instance Connect로 붙어보려 했는데 여기서도 `Failed to connect to your instance`가 떴다.
4. 인스턴스를 재부팅해봤지만 똑같았다.
5. 서버가 망가진 줄 알고 EC2를 새로 만들어서 옮겼는데, **새 서버도 똑같이 SSH만 안 됐다.**

**원인**

새로 만든 서버에서도 같은 증상이 나오는 걸 보고서야 서버가 아니라 내 쪽 문제라는 걸 알았다. 서버의 sshd 로그(`journalctl -u sshd`)를 열어보니 접속 시도가 `211.235.66.128`에서 온 걸로 찍혀 있었는데, 내가 `curl ipify.org`로 확인해서 보안그룹에 넣었던 IP는 `211.235.67.5`였다. 폰 테더링을 쓰고 있어서 나가는 경로에 따라 공인 IP가 다르게 잡혔던 것이다.

**해결**

보안그룹의 SSH 허용 대역을 서버 로그에 찍힌 IP 기준(`211.235.66.0/24`)으로 바꾸니까 바로 붙었다.

**여기서 배운 것**

접속이 안 될 때 "내가 확인한 내 IP"를 그대로 믿으면 안 된다. 접속을 받는 쪽 로그를 봐야 진짜 IP를 알 수 있다. 그리고 환경을 새로 만들었는데도 같은 증상이 나오면 환경 문제가 아니라 내 쪽 문제일 가능성이 크다.
